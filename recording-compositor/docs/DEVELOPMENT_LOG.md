# SmiRing Connect 録画機能 — 開発ノート

このドキュメントは、SmiRing Connect の録画機能を作る過程で行った試行錯誤・実測・その結果たどり着いた実装を、時系列で記録したものです。同じ勘違いを繰り返さないために、**何を疑い、どう検証し、何が正しかったか**を中心に書いています。「今のコードがこうなっている理由」を知りたい未来の自分(または別セッションのClaude)向けのノートです。

コードそのものの説明(データの流れ・スキーマ・セットアップ手順)は [`README.md`](../README.md) を参照してください。ここに書くのは**経緯**です。

---

## 0. 全体アーキテクチャの選定

最初に決めたのは「どこで録画し、どこで合成するか」でした。

- **録画(Track Egress)は Hetzner** — 既に LiveKit の SFU が動いている箱。コーデックコピーのみで再エンコードがなく、Room Composite Egress のようなヘッドレスChromeも不要なため、既存のライブ通話の負荷にほぼ影響しない。
- **合成(ffmpeg)は Cloud Run Jobs** — 重い処理なので、ライブ通話の生命線である Hetzner (CX33, 4vCPU) には置かない。バッチ処理として正しいプリミティブは Cloud Run Jobs であり、`workerRoutes.ts` のコメントが指摘する「レスポンス後はCPU保証がない」問題も回避できる。

レイアウトは意図的にシンプルにした: 画面共有ありなら「共有画面 + 顔最大10人」、なしなら「顔最大20人グリッド」。発言者強調は見送り(理由: インタラクティブ再生は個別ファイルの恒久保存が必要になり、一時ファイル削除の前提と矛盾するため)。

## 1. 最初の実装で踏んだバグ(このログの前段)

以下は、このログの詳細な試行錯誤パートに入る前に解決済みだった問題です。

### 1.1 Webhookが届かない(2つの独立したバグ)

- `req.get('Authorize')` という**タイポ**(正しくは `Authorization`)。録画に限らずWebhook依存の全機能(チャット掃除等)に影響していた古いバグ。
- LiveKitは `Content-Type: application/webhook+json` という非標準ヘッダでPOSTしてくる。グローバルの `express.json()` はこれにマッチせず、署名検証用の生ボディが取れていなかった。`express.raw()` をこのパスにだけ先に登録して解決。

### 1.2 R2キーのサニタイズがtrackIdを壊していた

`sanitizeKeyPart` の正規表現が `_` を `-` に変換していたため、LiveKitのtrackId(`TR_xxxx`)がR2キー内で壊れ、DBに保存した生のtrackIdと突き合わせられなくなっていた。「listEgressが開始時刻を返さない」という誤った仮説を最初に立てて `connect_recording_tracks` テーブルを自作するに至ったが、**本当の原因はこちらだった**。テーブル自体は「事後にAPIへ問い合わせるより、egress開始の瞬間に自分たちのDBへ書く方が依存が少ない」という利点があったため、原因判明後もそのまま採用を継続した。

### 1.3 A/Vジッターとタイムスタンプ

`started_at` を `DEFAULT now()`(DB側)ではなく `startTrackEgress` 呼び出し**前**に `new Date()` で明示的に取得するよう変更。ネットワーク往復(Hetzner⇔Cloud Run)の50〜300msのジッターがオフセットに乗るのを防いだ。

## 2. 「カメラOFFで開始したらズレる」問題

### 2.1 最初の観察と間違った仮説

ユーザー報告: 「ビデオ&マイクをOFFで入室し、その状態で録画を開始したら、ビデオがずっとONに見える(ズレている)」

**検証1**: `PreJoinScreen.tsx` を読み、「OFFで入室 = トラックを一度も publish していない」ことを確認。

**検証2**: 合成コードのロジックを静的に読み、「OFFで入室→後からON」というシナリオは正しく処理されるはずと結論づけた。

**検証3(実測)**: 実際のffmpegコード(`buildLayoutSegments`/`renderSegments`/`mixAudio`)を使い、合成 offsetMs=5000 のカメラトラックを持つ10秒の録画を合成する再現テストを組んだ。`blackdetect`で黒期間の境界を検証したところ `black_start:0 black_end:5` と**正確に一致**。→ **この時点では合成ロジック自体にバグは見つからなかった**。

ユーザー自身も報告を撤回(「あ、嘘かもです」)し、再調査を依頼。

### 2.2 本当の原因(ミュートは unpublish ではない)

再現できなかった理由を突き止めるため、`livekit-client` の `setTrackEnabled` の実装を直接読んだ:

```js
if (enabled) {
  if (track) { yield track.unmute(); }       // 既存publicationがあれば unmute のみ
  else { /* createTracks + publishTrack */ } // publicationが無い時だけ新規publish
}
```

これで**入室時ONだったが後でOFFにし、OFFのまま録画を開始したケース**が壊れる理由が分かった:

- `startRecordingForParticipants` は `participant.tracks` を **mutedかどうか関係なく全部** egress開始していた
- egressのPTSは「最初に本物のフレームを受信した時刻」を基準にする
- ミュート中のトラックにegressを張ると、DBの `started_at` は録画開始時刻(まだ映像が来ていない時点)を記録するが、実際の映像はしばらく後に届く
- → 「本当は後から来た映像なのに、録画開始と同時刻に配置されてズレる」

この仮説を裏付けるため、egress自体のソースコード(livekit/server-sdk-go の synchronizer)を読み、「最初のパケット受信時刻」を基準にPTSを組み立てるロジックがあることを確認した。

### 2.3 「録画中のON→OFF→ONは平気」という追加報告の検証

ユーザー: 「ONで録画開始→OFF→ONにしても大丈夫だった」

これは2.2の仮説と矛盾しない。理由:
- 録画開始時点でカメラがONなら、egressは最初から本物のフレームを受信しており、正しいPTS基準が確立される
- 途中でmuteされても(内部的には `MediaStreamTrack.stop()` されるだけ)、egressの同期ロジックは既に確立済みの基準を使うため、後で来る映像も正しい相対時刻で配置される

**実測で確認**: 「ON→10秒後にOFF→14秒後にON」という実際の録画をダウンロードし、`blackdetect`で解析したところ、黒期間が `12.1s〜26.0s`(13.9秒間)と**録画の途中に正確に**入っていた。前(開始直後)にもズレていない。→ **「録画開始時点で既にミュートされている」ケースだけが壊れる**、と結論を確定させた。

### 2.4 その場しのぎでは済まない: mute/unmuteはwebhookが飛ばない

最初の修正案(「録画開始時にミュート中のカメラを無視する」)を検討している最中に、重大な見落としに気づいた。`setTrackEnabled` を再度読むと:

- publicationが**一度でも存在すれば**、以後のON/OFFは全部 `mute()`/`unmute()`
- `track_published` webhookが飛ぶのは「そのセッションで初めてpublishした瞬間」だけ
- LiveKitには `track_muted`/`track_unmuted` というwebhookイベントが**存在しない**(SDKの型定義で確認)

つまり「録画開始時にミュート中カメラを無視する」だけを実装すると、**そのカメラが後で本当にONに戻っても、backendには一切通知が来ず、二度と録画されない**。これは元のバグより悪化する。

一方で朗報もあった: `participant_joined`/`participant_left` はwebhookとして**存在する**(SDKの型定義で確認)。入退室の追跡は無料で手に入る。

### 2.5 最終設計: フロントからの「確認して」トリガー + サーバー自身のlistParticipants

ミュート/アンミュートだけはpushの手段がないため、**クライアントから軽いping**を送る設計にした。ただし内容は一切信用しない:

- フロントは「何か変わったかも、確認して」としか送らない(状態そのものは送らない)
- backendは `listParticipants()` を呼んで**LiveKit自身の現在の状態**を取得し、それを正とする
- 記録する時刻は常にサーバー自身が `stopEgress`/`startTrackEgress` を呼んだ瞬間の `Date.now()`

これは既存の `track_published` webhookパスと全く同じ信頼モデル(webhookも「何か起きた」という通知に過ぎず、実際の時刻はサーバー側でスタンプする)。

この設計変更に伴い、データモデルを「1トラック=1行」から**「1トラック=複数の可視区間、各区間が1行」**に変更した(`connect_recording_tracks` に `segment_index`/`ended_at` を追加、R2キーにも連番を付与)。

**実装後の検証**: DBの部分ユニークインデックス(`WHERE ended_at IS NULL` で1トラックにつき未終了行を1つまでに制限)が実際に競合を弾くか、実DBに対してテストスクリプトで確認した(2本目の同時挿入が `duplicate key value` で拒否されることを確認)。

## 3. 「カメラOFFの人にもアイコンを出したい」

要件: 在室しているがカメラOFFの人は本人のアバター画像、そもそも不在の人は何も表示しない。

### 3.1 データモデルの拡張

- `pickFaces`(カメラのみを見る)を `pickParticipants` に置き換え、カメラ以外の任意のトラック(マイク等)の重なりも「在室」の証拠として扱うようにした
- ただし「マイクも切って入室した人」はどのトラックも持たないため、**在室そのものを独立して追跡する必要がある** → `connect_recording_participants` テーブルを新設(`participant_joined`/`participant_left` webhookで更新)
- `buildLayoutSegments` の区間の切れ目も、カメラ・画面共有だけでなく在室の開始/終了でも切るように拡張

### 3.2 アバター画像の取得元の特定

フロントの `avatar_link` がどこから来ているかを `basic_profile_info.avatar_id` → `gallery.storage_path`/`thumbnail_path` → R2、と backend のコードを読んで特定。compositor自身のservice-role Supabaseクライアントで同じ経路を辿れることを確認した。

### 3.3 実装と実測検証

ffmpegの `overlay` フィルタでアバター画像をタイル中央に配置する処理を実装。**合成テストで検証**: 実際にレンダリングした画像から、アバター中心のピクセル色(`fda400` オレンジ)、背景のピクセル色(`1a1a1a`)、タイル外(`010103` 黒)をサンプリングし、期待通りであることを確認。

### 3.4 デプロイ順序のミス

アバター実装後、ユーザーが「一人で入っても出ない」と報告。調査したところ、**コミットはされていたがCloud Run Jobには反映されていなかった**(手動 `gcloud run jobs deploy` が必要なことを失念)。イメージのビルド時刻とコミット時刻を突き合わせて確定させた。以後、コード変更のたびに「Jobへのデプロイが必要か」を明示的に確認するようにした。

## 4. Egressボットが在室テーブルを汚染した

デプロイ後もアバターが0件のまま。ログに決定的なエラーが出ていた:

```
invalid input syntax for type uuid: "EG_fNrUnjNW5UPY"
```

### 4.1 原因調査

`connect_recording_participants` の実データを見ると、`EG_` で始まる非UUIDの行が大量に混入していた(実ユーザー3人に対し記録12件)。

**原因**: LiveKitのEgress自体が、トラックを購読するために**隠れた参加者としてルームに接続する**。そのため新設した `participant_joined`/`participant_left` webhookが**Egressボット自身**にも発火していた。

`basic_profile_info.id IN (...)` のUUID型クエリに非UUID文字列が1つでも混ざると**クエリ全体が失敗**し、実在する3人分のアバターまで巻き添えで0件になっていた。

### 4.2 修正

`ParticipantInfo.kind === EGRESS` を webhookハンドラと録画開始時の参加者一覧の両方でフィルタ。加えて、同種の異常が再発してもアバター機能全体が巻き添えを食わないよう、compositor側にもUUID形式チェックを防御的に追加した(1箇所の不備が全体を落とす設計を避ける)。

## 5. 合成時の映像の点滅・黒画面(セグメント継ぎ目の問題)

ユーザー: 「共有した画面が点滅する、1秒くらい暗くなる」

### 5.1 原因1: `-ss` のaccurate seekがフレームを間引く

**再現テスト**: 5秒に1フレームしか送らない「まばらな」ソース(静止した共有画面を模したもの)を作り、任意の境界で切って合成した。ソースは全編真っ白なのに、**境界の直後が3.2秒間真っ黒**になった。

原因: `-ss` の accurate seek は「シーク位置よりPTSが前のフレーム」を破棄する。まばらなソースでシーク位置がフレームとフレームの間に落ちると、その時点で表示されるべきフレームがそもそも読み込まれない。カメラ(30fps)ではほぼ起きないが、静止した共有画面では頻発する。

**修正**: 各タイルをシーク位置より前からデコードし、余分をフィルタグラフ側で `trim` する方式に変更(`fps` フィルタでギャップを埋めてから `trim`)。再現テストで黒フレームがゼロになることを確認。

### 5.2 原因2: 無駄な継ぎ目そのもの

Egressボットの入退室が在室テーブルに紛れ込んだ結果、実トラック境界11個に対し**セグメントが31個**に細切れになっていた(4章の問題と複合していた)。

**修正**: 描画内容が完全に同一な連続セグメントを結合するロジックを追加。テストで20個の無意味な境界が2セグメントに集約されることを確認。

## 6. 「配信が止まると黒くなる」問題(egressが実時間より長く動く)

ユーザー: 「タブ切替やPiP操作をすると、共有画面が真っ暗になる」

### 6.1 実測による原因の特定

領域ごとに黒を検出したところ、**すべて「セグメント途中で始まり、次の境界ちょうどで終わる」**という一貫したパターンだった。生ファイルの実際のフレーム時刻を確認すると、素材は最後まで届いていた(1秒に1回のペースで)。つまり「素材が尽きた」のではなく、**合成側がそれを取りこぼしていた**。

再現テスト: 「実際は30秒の素材」に「60秒ある」と嘘のdurationを与えて25秒のセグメントを描かせたところ、**素材が尽きた10秒地点から真っ黒**になった。原因は `overlay` の `eof_action=pass`(タイルの映像が尽きると下地の黒が透ける)。

**なぜ嘘のdurationが生まれるか**: 配信側(ブラウザ)がフレーム送信を止めても、egress自体は動き続ける。ファイルの申告尺は実際の最終フレームよりずっと長くなり得る。

### 6.2 修正: 最後のフレームを保持 + 実在フレームへのシーク

- `tpad` の `stop_mode=clone` で、映像が尽きたら最後のフレームを保持し続けるようにした(通話中に実際に見えていた「フリーズ」と同じ挙動)
- 各ファイルのフレーム時刻をコンテナのインデックスから読み(デコード不要、0.02秒)、切れ目の時点で実在するフレームからデコードを開始するよう変更(15秒固定の先読みより正確)

両方とも合成テストで黒が消えることを確認。

## 7. カメラが複数の録画に同時に記録されていた

ユーザー: 「画質が変わる瞬間に必ずジャンプする。音声だけが最後に余る」

### 7.1 診断ログの追加

推測で直すのを避けるため、まず「トラックごとにegressの稼働時間 vs ファイルの実尺」を比較するログ機能(`reportTimelineFidelity`)を追加してデプロイし、実際の録画で測定した。

### 7.2 決定的な数字

```
camera seg0 | offset 17.7s | media 214.4s | wall 25.6s  | missing -188.8s
camera seg1 | offset 55.8s | media 205.5s | wall 178.4s
```

ファイルは短いのではなく、**egressの稼働時間よりはるかに長い**。seg1は「55.8秒開始→録画終了」に対しファイルの実尺も同じだけあった。つまり**停止したはずのegressが最後まで回り続けていた**。

### 7.3 原因

1. `stopTrackRecording` が停止対象を `listEgress` からtrackIdで検索していたため、同じtrackIdのegressが複数あると**最初の1本しか止まらなかった**
2. `/recording/sync` の同時実行で、egressを開始してから行を挿入していたため、**二重起動を防げていなかった**(0.3秒差で同じ長さのファイルが2本、という痕跡から発覚)

結果、1つのカメラに対して開始時刻の違う録画が同時に複数走り、合成時にどちらが選ばれるかで映像がジャンプしていた。

### 7.4 修正

- egress開始時に `egressId` を保存し、IDで確実に停止する
- 行の挿入を**先に**行い、DBの部分ユニークインデックス(`WHERE ended_at IS NULL`)で「1トラックにつき未終了行1つまで」を保証。実DBで排他制御が効くことをテストスクリプトで確認
- 合成側にも防御を追加: ファイルの使用可能長をegressの稼働時間に切り詰める(同種の異常が再発しても被害が出ないように)

### 7.5 副作用: 前回のデバッグ用ファイルが次の録画に混入

診断のため一時ファイルを削除せず残す設定(`KEEP_TEMP_TRACKS=1`)を入れていたが、一時ファイルのパスが**ルーム単位**(`recordings-tmp/<room>/`)で録画ID単位ではなかったため、**前回の録画の残骸を次の録画が拾ってしまった**。しかも「行が無いファイルはオフセット0に配置する」というフォールバックがあったため、前回の会議の音声・映像が今回の録画の先頭に全部重なった。

**修正**:
- 一時ファイルのパスを `recordings-tmp/<room>/<recordingId>/` に変更(録画ごとに隔離)
- 「行が無いファイルは配置せず破棄」に変更(位置を推測するより捨てる方が安全、という判断)
- 汚染されたR2ファイルとDB行を手動で特定・削除し、該当録画を再合成して救出した

## 8. 画面共有とカメラの同時再生で画面が真っ暗になる

ユーザー: 「共有しながらカメラOFFにすると、画面共有部分も真っ暗になる」「画質切替のたびにジャンプする」

### 8.1 切り分けの過程(推測を避けて1つずつ確認)

1. まず「複数解像度を含むVP8ファイル」を合成パイプラインに通して、**解像度変化自体は正しく処理される**ことを確認(赤5秒→緑5秒のテストで色の境界が正確)。→ 合成ロジックのバグではないと判明。
2. 実際の録画ファイル(カメラ+共有画面)をダウンロードし、生ファイルの該当時刻のフレームが実際に黒いかを直接確認 → **黒くない**(素材は正常)。
3. 「共有タイル単体」では黒くならないが、「共有+カメラの2タイル」にすると黒くなることを実ファイルで再現。
4. フィルタの各要素(`tpad`, `fps`の順序, `eof_action`)を1つずつ変えて切り分けたが、いずれも再現/非再現が一貫しない → **判定方法(blackdetectの閾値)が甘く、誤判定していた**ことに気づき、ピクセル直接サンプリングに切り替えて仕切り直し。
5. 「2つ目のファイル入力を使わない」「カメラを事前に別ファイルへ変換してから合成」では共有が正常、「カメラの生WebMを同一フィルタグラフ内でデコード」すると共有が黒くなる、と特定。
6. 生ファイルを直接 `ffmpeg -i ... -f null -` でフルデコードし、エラー出力を確認:

```
cam_b.webm: Application provided invalid, non monotonically increasing dts to muxer in stream 0: 32 >= 32
```

### 8.2 根本原因

カメラのファイルには**タイムスタンプの重複・逆行**があった。これはsimulcastのレイヤー切替(画質変更)のタイミングで、egressが別レイヤーのフレームを同じ時刻で書き込むために起きる。

**重要な発見**: この壊れたタイムスタンプは自分自身のファイルだけでなく、**同一フィルタグラフ内の他の入力にも影響する**。壊れたファイルがグラフのスケジューリングを崩し、もう一方のタイル(共有画面)のフレームが捨てられていた。カメラ自身は平然と再生され続けるため、「共有だけ真っ暗になる」という不可解な症状になっていた。

### 8.3 修正: 合成前にCFR(固定フレームレート)へ正規化

各映像トラックを合成前に `-fflags +genpts` で再エンコードし、タイムスタンプを作り直すようにした(`normalizeVideo`)。実際の生ファイルで検証: 正規化前は共有タイルが全時刻 `000000`(黒)、正規化後は全時刻 `ffffff`(正常)。

---

## 9. 正規化の副作用: 画質が固定されてしまった

ユーザー: 「顔の画質がずっと悪い」「共有画面が緑にぐちゃぐちゃになる」

### 9.1 原因

8.3の `normalizeVideo` に**解像度を指定していなかった**。ffmpegは何も指定しないと最初のフレームでエンコーダを初期化し、以降のフレームを強制的にそこへ合わせる。simulcastの最初のフレームは**最低画質レイヤー**(立ち上がり時)であるため、通話全体の720p映像が320x180に潰されていた。

実測: `cam_a.webm` は 1280x720/640x360/320x180 の3レイヤーを含むが、正規化後は320x180固定になっていた。

共有画面についても同様に、Retinaディスプレイの3174x2410を含むファイルが948x720(最初のキーフレームの解像度)に固定されていた。緑のノイズは、レイヤー切替のたびにスケーラが再初期化される経路で発生していると推測(ただし直接の再現・確定はできていない)。

### 9.2 修正

キーフレームのみを読んで(デコード不要)、そのトラックが**実際に含む最大解像度**を求め、全フレームを明示的にそのサイズへ変換するよう修正(`probeBestResolution`)。キャンバスサイズを上限とし、録画されている以上には引き伸ばさない。

実測: カメラの解像度が320x180→**1280x720**に、情報量が267→**2276バイト/フレーム**(8.5倍)に改善。尺は変化なし(誤差1フレーム以内)。これまでの回帰テスト(アイコン表示・タイミング・セグメント継ぎ目)もすべて再実行し、影響がないことを確認した。

## 10. 合成の進捗表示

ユーザー: 「準備中のままいつ終わるか分からず不安になる」という声を受けて実装。

- compositorの各フェーズ(ダウンロード30% / 描画55% / 仕上げ15%)を実際にかかる時間の比率で重み付け
- 描画フェーズ内はセグメント**数**ではなく**尺**で按分(長い区間1つ+短い区間多数、という構成が普通なため)
- 99%で止め、100%は「completed」ステータス自体に譲る(進捗が100%なのにステータスが「準備中」のままという矛盾状態を作らないため)
- 実際に重みを流し込んだテストで、単調増加(8%→...→99%→完了)することを確認

フロント側は「合成中」の表記を「準備中」に変更し、準備中のものがある間だけ5秒ごとにポーリングするようにした。

## 11. 負荷の実測と、それに基づく最適化

「3人+画面共有+録画でCX33のCPUが150%(=1.5コア)になる。30人だと壊れるのでは」という懸念から、
推測で対策する前に実測した。**結果として、当初立てた仮説のほとんどが外れた。**

### 11.1 外れた仮説1: 「`track_cpu_cost` の予約枠で録画が拒否される」

Egressの Monitor は `available = コア数 × max_cpu_utilization − 予約合計` で受理/拒否を判断し、
Track Egress 1本の既定予約は `0.5`。4コアなら `4 × 0.8 ÷ 0.5 = 6本` が上限になる計算で、
「30人(60トラック)では大半が拒否される」と予測した。

**実測では8ジョブ同時でも拒否は1件も出なかった。** 予約値が効くのはジョブ開始から15秒だけで、
その後は実測CPUベースに切り替わるため。Track Egress の実測は予約値よりずっと小さいので、
先行ジョブが落ち着くと枠が空いて後続が通る。つまりこの予約枠は「同時に大量起動したときの
バースト制御」であって、定常状態の同時本数の上限ではない。

→ **「拒否されて録画が欠ける」より「拒否されずに受理されて箱が詰む」方が現実的なリスク**、
という理解に修正した。`track_cpu_cost` を下げる対策は採用していない(下げても箱は速くならず、
むしろCPUが張り付いたときに `cpu_kill_grace_sec` でジョブが**途中で殺される**方に倒れるため)。

### 11.2 外れた仮説2: 「画面共有(6Mbps・Retina解像度)が突出して重い」

`docker compose top egress` の TIME列(累積CPU秒)を時間差で撮り、ジョブ単位の実測を取った。

| トラック種別 | 実測CPU |
|---|---|
| マイク | 約 0.03〜0.04コア |
| カメラ・画面共有 | 約 0.06〜0.11コア |

カメラ(720p/1.7Mbps)と画面共有(6Mbps/3174x2410)が**ほぼ同じコスト帯**だった。
Track Egress はコーデックコピーのみで再エンコードしないため、バイト数よりも
「1トラックぶんの処理オーバーヘッド(プロセス + SFUへの接続 + RTP処理)」が支配的。

→ **コストはトラックの「本数」に比例し、「ビットレート・解像度」にはあまり比例しない。**
これが今回の最適化方針を決めた一番大きい発見。

### 11.3 計測方法そのものの検証

`docker stats`(cgroup全体)と `docker compose top` のTIME差分(プロセス単位の積み上げ)を
**同じ瞬間に撮って突き合わせた**: 0.334コア vs 0.297コア でほぼ一致。カーネル側の
ネットワーク処理など、プロセスに帰属しない見えないコストは無いと確認できた。

なお `docker stats` の CPU% は **100% = 1コア**(4コアなら最大400%)。ここを取り違えると
すべての試算が4倍ずれる。

補足: LiveKit自身が出す `hw resources usage` ログは `tini`/`pulseaudio`/`egress`本体しか
見ておらず、実際に働く `run-handler` は対象外で常に `lastCPU: 0`。**このログは使えない。**

また `lk load-test --video-publishers N` は**送るだけで何も購読しない**(公式ドキュメントに
"with no subscribers" と明記)。egress は他の参加者の購読状況と無関係に自分でトラックを購読
するので**録画コストの計測には問題ない**が、「30人が互いのグリッドを見合う」下り方向の
負荷は再現できない。そちらを測るには `--subscribers` が要る(今回は未実施)。

### 11.4 採用した対策

実測を踏まえ、**本数を減らす施策を主軸に、画質は「下げても損しない、むしろ改善する」部分だけ**に絞った。

1. **録画カメラの本数上限**(`MAX_RECORDED_CAMERAS`、既定20) — 人数に比例して効く唯一の対策。
   ライブ通話は不変で、溢れた人は既存のアバタータイル経路に落ちる。

   実装時に**枠が解放されないバグを踏みかけた**: 退室しても
   `connect_recording_tracks` の行は `ended_at = NULL` のまま残る(行を閉じるのは
   `syncCameraRecordings` だけで、それは `listParticipants()` を回すため退室済みの人は
   永遠に対象外。`track_unpublished` のwebhookハンドラも無い)。上限を入れるまでは無害
   だったが、`openCameraCount` がその行を数えるため、**最初の20人が抜けた後も枠が埋まった
   ままになり、残った人が最後までアイコンのまま**になる。対策として `participant_left` で
   (1) `closeParticipantTracks` が行を閉じて枠を返し、(2) その場で `syncCameraRecordings`
   を回して空いた枠を埋める(枠が空く瞬間＝退室時なので、そこが埋めどき)。

   なお **egress が自分で死んだ場合(Monitor の CPU kill、ネットワーク断など)は今も行が
   開いたままになり、枠を1つ握ったままになる**。上限を入れる前は「そのカメラが録画され
   なくなる」だけだったが、今は枠も道連れになる。`listEgress` と突き合わせて自己修復する
   案はあるが、開始直後のegressがまだactiveに現れない競合で誤って閉じるリスクがあるため、
   現時点では未対応。

   副次効果として、
   録画対象外のカメラは**dynacastが復活する**(録画中のカメラはegressが最上位レイヤーを購読
   するため常に720pを送らされるが、対象外なら視聴者が必要とする分だけで済む)。これは
   サーバーより**参加者本人の上り帯域とバッテリー**を助ける
2. **画面共有を1920x1080にキャップ + 4Mbps** — 現状は `ScreenSharePresets.original`
   (リサイズなし)で、Retina実測3174x2410に6Mbpsを配ると **0.052 bits/pixel** しかない。
   1080p/4Mbpsなら **0.129 bits/pixel(2.5倍)** で、**帯域を削りながら字は読みやすくなる**。
   共有者PCのエンコードも7.6MP→2.1MPに減る
3. **画面共有のsimulcastを2レイヤーに** — メインを1080pにキャップした時点で `h1080fps15`
   レイヤーは重複。共有者のエンコードが3回→2回になる
4. **合成を30fps→15fps** — 画面共有は元々15fps配信なので半分は複製フレーム。
   Cloud Run Job の実行時間(=課金)と「準備中」の待ち時間が約40%減る。あわせて
   `VIDEO_ARGS` から `-r` を外した(`filter(arg => arg !== String(FPS))` と**値で除外**
   していたため、FPSを23にすると `-crf 23` の値まで消える地雷になっていた)

### 11.5 採用しなかったもの

- **カメラの配信画質を下げる(h720→h540)** — 11.2の通りCPUにほとんど効かない一方、
  1対1・ピン留め・スピーカービューでは劣化が直接見える。**払うUXコストに見合わない**ので温存
- **共有中だけカメラ画質を落とす** — `LocalVideoTrack.setPublishingQuality()` で
  再publishせずに実現可能だが、dynacastが同じAPIを呼ぶため上書きされるリスクがある。
  効くのも主にCloud Run側(ダウンロード・正規化の量)なので、上記4つの効果を見てから再検討
- **音声を `audio_only` RoomComposite 1本に統合** — マイク30本(約1.2コア)を1ジョブに
  できる。`ShouldUseSDKSource()` が `audio_only && layout=="" && custom_base_url==""` の
  ときChromeを使わないSDKソース経路に入るため軽い。30人で本当に詰まったときの第一候補
- **egressを別マシンに分離** — LiveKit公式は同居を非推奨としているが、サーバー費用が
  1.7倍になるため予算上不採用

## 全体を通しての教訓

1. **「音声は常に正しい」という不変条件が、切り分けの最強の武器になった**。マイクはミュートしても無音を送り続けるため時間軸が壊れようがない。映像だけがズレる/ジャンプする場合、常に「音声を基準に何が違うか」を最初に確認すると、原因の当たりが早くつく。

2. **推測で直さず、生データで確認する**。「たぶんこう」で実装すると、当初の見立てが外れていたことが何度もあった(ファイルが短いと思ったら実は長かった、セグメント境界の問題だと思ったらegressの多重起動だった等)。`KEEP_TEMP_TRACKS` で一次データを残せるようにしたことが、後半の調査の速度を大きく上げた。

3. **一つの修正が新しい問題を作ることがある**。egressの多重起動を直すために一時ファイルを残したら、それが次の録画に混入した。正規化でタイムスタンプ問題を直したら画質が固定される副作用が出た。**直したら回帰テストを一式流す**運用を徹底した。

4. **LiveKitの内部動作は「参加者の視点」と「サーバーの視点」で見えるものが違う**。ミュート状態はブラウザ同士ならリアルタイムに同期されるが、webhookには存在しない。Egress自体も「隠れた参加者」としてルームに現れる。ドキュメントより実装(SDKのソース、protocolの型定義)を直接読むことが何度も突破口になった。

5. **性能の話は、単位と計測方法を先に検証する**(11章)。`docker stats` の 100% が1コアなのか全体なのかを取り違えるだけで試算が4倍ずれるし、「使えそうなログ」が実は常に0を返していることもある。**独立した2つの方法で測って一致するか**を確認してから、その数字の上に結論を積む。今回は最適化の方針そのもの(「画質を下げる」→「本数を減らす」)が実測でひっくり返った。
